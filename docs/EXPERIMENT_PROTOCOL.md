# AgentRec 预注册实验协议

本文件在正式实验前冻结。后续修改需要在报告中记录修改原因和影响范围。

## 1. 研究问题

面对模糊需求、动态偏好、多购买对象和硬约束时，具备规划、主动澄清、工具调用、分层记忆与失败重规划的 Agent，是否比固定推荐流水线或简单记忆 Agent 更可靠、高效地完成购物任务？

## 2. 预设假设

- **H1（主要）**：完整 Agent 相比固定流水线提高端到端任务成功率。
- **H2（主要）**：分层记忆相比扁平记忆降低跨对象画像污染率并提高硬约束满足率。
- **H3（次要）**：主动澄清提高初始信息不足任务的成功率，代价是增加交互轮数。
- **H4（次要）**：失败反思与重规划提高第一次推荐被拒绝后的恢复成功率。
- **H5（探索）**：分层记忆可能改善 HR/NDCG，但该结果不是项目成立的必要条件。

## 3. 场景分层

测试集至少覆盖：

1. 清晰单轮需求。
2. 信息不足、必须澄清。
3. 稳定偏好与当前意图一致。
4. 稳定偏好与短期意图冲突。
5. 为本人和为他人购物切换。
6. 明确预算、禁忌、尺寸等硬约束。
7. 第一次推荐被拒绝并给出新反馈。
8. 冷启动用户或冷启动商品。

每类任务数量、受控/真实来源比例和难度必须在运行清单中报告。

## 4. 主实验组

| ID | 系统 | 说明 |
|---|---|---|
| B0 | Fixed pipeline | 固定搜索→过滤→排序→推荐，无自主决策 |
| B1 | Agent / no memory | 有规划与工具，但跨轮不读写偏好记忆 |
| B2 | Agent / flat memory | 所有偏好写入一个扁平画像 |
| B3 | Agent / hierarchical memory | 稳定、阶段、会话、对象、约束、事件分层 |
| F | Full Agent | B3 + 主动澄清 + 失败反思与重规划 |

## 5. 消融组

- F - clarification：禁止主动追问。
- F - replanning：拒绝后不反思，只做相同流程重试。
- F - recipient isolation：对象偏好与本人偏好合并。
- F - temporal decay：阶段/会话偏好永不过期。
- 可选 F - tools：不给外部商品查询，只凭模型上下文回答。

不要同时删除多个模块后声称定位了单一机制。

## 6. 指标

### 主要指标

- `task_success_rate`：最终选择满足任务确定性验收条件。
- `hard_constraint_satisfaction_rate`：所有硬约束均满足。
- `profile_contamination_rate`：不属于本人的偏好被写入本人稳定画像的比例，越低越好。
- `recovery_success_rate`：第一次失败/拒绝后最终成功的比例。

### 次要 Agent 指标

- 有价值澄清率与无效澄清率。
- 工具调用成功率、冗余调用率和平均调用数。
- 记忆写入准确率、正确召回率、过期记忆误用率。
- 平均轮数、延迟、token 和估算成本。
- 解释忠实度：解释中的属性能否在商品或记忆证据中找到。

### 推荐辅助指标

- HR@1/3/5、NDCG@3/5、Recall@5。
- 如候选池允许，再报告覆盖率和类别多样性。

## 7. 公平控制

- 所有实验组使用同一任务、商品目录、候选池和用户模拟器。
- 相同 LLM、temperature、最大输出、上下文和工具预算；若上下文长度因记忆方案不同而变化，单独报告。
- 工具返回结果排序固定；所有随机源记录 seed。
- pilot 之后冻结主测试集。开发调试只能使用单独的 dev 集。
- LLM Judge 不得作为唯一主指标；能确定性校验的约束必须用代码校验。

## 8. 样本量与统计

- smoke：20 个任务，不用于结论。
- pilot：最多 100 个任务，每组至少一次完整运行，用于发现实现和协议问题。
- full：建议 300–1000 个任务；随机 Agent 运行至少 3 个 seed，受预算限制时必须披露。
- 比例指标报告 bootstrap 95% 置信区间；组间比较尽量使用相同任务的 paired bootstrap。
- 同时报告绝对差值、相对差值和失败样本数，不只报告百分比。

## 9. Pilot 决策门

pilot 的目标不是挑选最好看的结果，而是回答：

- Agent 是否真的根据状态选择了不同动作？
- 工具和记忆是否在轨迹里被实际使用？
- 指标实现是否经过手工案例核验？
- 分层记忆是否至少在对象隔离或硬约束场景出现机制信号？

如果没有信号，先检查任务是否能区分方法、记忆是否被召回、LLM 是否遵循工具结果。任何协议调整都在 full 运行前记录并冻结。

## 10. 结果解释矩阵

| 排序指标 | Agent 可靠性指标 | 结论 |
|---|---|---|
| 上升 | 上升 | 整体正向结果 |
| 基本不变 | 上升 | 可靠性与可控性提升，主假设仍可成立 |
| 上升 | 下降 | 个性化收益伴随约束/安全代价 |
| 基本不变或下降 | 基本不变 | 报告零/负结果，定位规划、召回或更新机制失败 |

任何情况下都保留完整轨迹和失败分析，不得只保留成功样本。

## 11. 结果文件合同

每条运行至少写出：

```json
{
  "run_id": "...",
  "config_hash": "...",
  "git_commit": "...",
  "task_id": "...",
  "scenario": "recipient_shift",
  "seed": 42,
  "system": "hierarchical_memory",
  "trajectory": [],
  "final_product_ids": [],
  "metrics": {},
  "latency_ms": 0,
  "token_usage": {},
  "error": null
}
```

聚合结果必须保存样本数、均值、置信区间、失败数、配置 hash 和代码 commit。
